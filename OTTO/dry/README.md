# OTTO DRY 시험 수집

독일 OTTO `Trockner` Topseller 검색의 상단부터 매번 새로 탐색해 적격 상품을 최대 300개 수집한다.
제외·상품명 중복 제거 후 main_rank는 1~300까지 연속 부여하고, 같은 행의 bsr_rank는 상위 100개에만 동일하게 부여한다.
main 101위 이후 BSR은 CSV 빈값·DB NULL이며, 별도 BSR 행이나 요청을 만들지 않는다. 300개를 모으면 종료한다.
페이지 수를 고정하지 않으며 실제 검색이 먼저 끝나면 확보한 수량만 저장한다. 290개를 확보했다면 290행이 정상 결과다.
요청 실패·반복 페이지·응답 구조 변경은 검색 끝으로 취급하지 않는다.
확실한 비건조기만 제외한다. 일반 `Trockner`/`Wäschetrockner`나 제품 종류가 불명확한 검색 결과도 정보 부족만으로 제외하지 않고 포함한다. 상품명과 사양의 종류가 충돌하면 포함하고 검수 대상으로 표시한다. 판매 구성에 세탁기와 건조기가 함께 명시된 묶음은 제외한다. 제외·애매한 판단에는 출처와 최대 500자의 판단 문장을 남긴다. 애매한 상품은 진단 로그의 `needs_review=true`와 `ambiguous` 수량으로 별도 표시한다. 일부 비대상 상품이 포함될 수 있으며 첫 100개에서 검수한다. 90%는 허용 수준의 목표이며 실제 정확도는 검수 전 보장하지 않는다.

## 원격 실행 (Windows 명령 프롬프트)

휴대용 건조기 본품(`Portabler Wäschetrockner` 등)과 건조대용 송풍기 본품(`Lüfter für Wäscheständer`)이 제목에 명시되면 제외한다. 일반 `Wäschetrockner` 표시와 함께 있어도 이 명시적 본품 판정을 우선한다. 팬 기능·앱 제어·호환성·동봉 악세사리 설명만으로는 제외하지 않는다.
휴대용 표현은 건조기 본체를 직접 수식하거나 본체의 속성으로 명시된 경우에만 적용한다. `mobile Fernsteuerung`, `tragbare Fernbedienung` 같은 제어·부속품 설명은 건조기의 휴대 여부로 사용하지 않는다. 실제 휴대용 본품에 앱 기능이 함께 있어도 제외는 유지한다.

프로젝트에서 사용하던 Python 환경과 DB 설정을 사용한다. 코드를 원격에 반영한 뒤 실행한다.

```bat
cd /d C:\samsung_dx_seg
call OTTO\run_dry.bat --limit 300 --table dx_seg.dx_seg_ldy_dryer_retail_test
```

기본값이 위와 같으므로 별도 환경변수 설정이 없다면 `call OTTO\run_dry.bat`도 가능하다.
CLI가 환경변수 `OTTO_DRY_LIMIT`, `OTTO_DRY_TABLE`, `OTTO_DRY_OUTPUT_ROOT`보다 우선한다.
100개만 수집하려면 `call OTTO\run_dry.bat --limit 100 --table dx_seg.dx_seg_ldy_dryer_retail_test`를 사용한다.
허용 수량은 1~300이며 범위 밖 설정은 사이트·DB 요청 전에 거부한다. 시작 로그의 `target`과 `bsr_limit`에 실제 적용값을 표시한다.
통합 BAT·메일·운영 전환·DB 과거값 보충은 이 흐름에 포함하지 않았다.

기존 CSV 재적재: 실행 마지막에 출력된 **실제 CSV 경로**를 넣는다.

```bat
cd /d C:\samsung_dx_seg
call OTTO\run_dry.bat --load-only "C:\samsung_dx_seg\OTTO\dry\data\output\실제_batch_id\otto_dry.csv" --table dx_seg.dx_seg_ldy_dryer_retail_test
```

CSV와 같은 폴더의 `state.json`을 함께 보존해야 한다. 재적재 시 사이트에 접속하지 않는다.
완료 또는 실제 결과 부족으로 종료된 CSV만 적재한다. 수집 실패 중간 CSV는 검수용으로 보존하되 적재하지 않는다.
기존 100개 CSV와 과거 `collection_status=shortfall` 상태 파일도 읽을 수 있다.
재적재에서도 main 1~100은 동일 BSR, main 101~300은 빈 BSR이어야 한다. 원래 수집의 오류 통계는 재적재 상태에도 보존한다.
CSV가 변경됐거나 같은 배치가 다른 내용으로 이미 존재하면 중단한다.
동일 배치·동일 내용은 DB 트랜잭션 잠금 후 삽입 0건/중복 N건으로 끝낸다.
DB 적재는 한 트랜잭션으로 처리하며, 별도 테이블 생성·변경·기존 행 삭제는 하지 않는다.

## 결과 파일

기본 폴더: `OTTO/dry/data/output/<batch_id>/`

새 배치는 `o_dry_YYYYMMDD_HHMMSS` 형식이다(예: `o_dry_20261023_123431`).
하루 1회 예약 실행을 전제로 하며 충돌 대기·재시도는 추가하지 않았다. 이미 있는 실행 폴더는 덮어쓰지 않는다.
과거 접미사가 있는 CSV도 재적재할 때 원래 batch_id를 유지한다.

- `otto_dry.csv`: UTF-8 BOM, 요청한 20개 컬럼. 상품 처리마다 저장하며 id는 빈값.
- `state.json`: 배치, 진행 상태, CSV 검증값, 목표/실제/실패 수, 단계별 시간, 빈값 수, DB 결과.
- `run.log`: UTF-8 상세 로그. 콘솔에도 즉시 출력.
- `diagnostics.jsonl`: 상품 분류·출처/원본값/정규화값·충돌·별점 상태·오류 요약.
- 재적재 로그/상태는 원래 폴더의 `reload_<실행시각>_<고유값>/`에 따로 보존.

종료 코드: 0=목표 도달 또는 실제 검색 종료 후 적재 완료(일부 정보의 NULL은 가능),
2=행 수집 실패·요청/추출 실패·할인율 확인 경고, 3=전체 수집 실패,
4=DB 구조 확인/적재 실패, 5=시작 설정/CSV 검증 실패.
코드 2에서도 확보한 적격 행은 적재하며, 확인하지 못한 필드는 NULL로 유지한다.
실제 검색 종료로 목표보다 적게 확보한 사실만으로 코드 2를 반환하지 않는다.
새 수집의 정상 종료 상태는 `collection_status=complete`이며 `end_reason=target_reached/actual_search_end`로 원인을 구분한다.
기존 `shortfall_reason` 필드는 실제 검색 종료 시 남은 수량·제외·중복 등을 설명하는 정보로 유지하며, 오류 여부는 별도 실패 통계로 판단한다.
PDF 링크나 명시값을 확인하지 못한 사실만으로 코드 2를 반환하지 않는다. 실제 요청·추출 실패는 다른 출처에서 보완돼도 경고를 유지한다.

진단의 `product_result.row_saved=true`는 해당 행을 CSV에 저장했다는 뜻이다. DB 저장 결과는 `db_status`와 `database`에서 별도로 확인한다.
`status=collected/supplemented`는 기본 수집/보완 수집 경로이며, 정보 완전성이나 오류 없음의 보장이 아니다. `missing_fields`와 `issues`를 함께 확인한다.

| counts 항목 | 의미 |
| --- | --- |
| eligible / output_rows | 확보한 행 / 최종 보존된 CSV 행 수 |
| item_failures | 상품정보·식별값 확보 실패로 행을 저장하지 못한 건수 |
| supplemented_items | PDF 또는 상품명 SKU 보완으로 값을 확보한 행 수 |
| incomplete_items | SKU·용량·투입 방식·판매가·평점/평가 수 중 미확보 값이 있는 행 수 |
| request_error_items / extraction_error_items | 최종 출처 처리에 요청/추출 실패가 남은 저장 행 수. 다른 출처의 보완 여부와 별개 |
| price_warning_items | 원가·최종가격은 있는데 할인율이 없는 행 수 |

위 상태는 겹칠 수 있으므로 합해서 상품 수로 해석하지 않는다. 요청별 재시도 이력은 `request_end`에 별도로 보존한다.
DB 구조 확인이 처음부터 실패하면 사이트 수집을 시작하지 않는다.

## 수집 범위와 출처

LDY의 검색 URL 생성·광고 슬롯 배치, 비교표 옵션별 사양 파서, 모델 정리,
최신 평점 파서/검증만 재사용한다. 기존 전체 파이프라인을 실행하지 않는다.
리뷰 본문/페이지 이동, 추천 상품, 배송, 인기, 광고 컬럼, 스티커/OCR,
에너지 소비량을 위한 추출·요청·저장을 하지 않는다.

비교표 이름은 해당 옵션의 상품 링크 안에 있는 제목·부제에서 읽는다. 제목을 확인하지 못하면 `comparison_title_reason`을 남기고 목록명 등 다음 출처를 사용한다. 긴 기능 설명을 제목으로 대체하지 않는다.

SKU: 해당 옵션 비교표 모델 → 해당 옵션 목록에 연결된 PDF → 목록명 전용 추출/공통 형태 보완.
용량: 비교표 긴 제목 → 목록명 → 기존 검색 결과의 긴 제목 → 목록 용량 요약 → 비교표 용량 → 해당 상품 PDF.
투입 방식: 비교표 제목 → Beladung → Bauart → 실제 응답에 제공된 건조기 카테고리 표현 → 해당 상품 PDF의 명시값.
`Front loader`/`Top-loading`만 사용하며, 실제 근거가 없으면 빈값이다.
세탁기 카테고리 요청이나 모든 건조기의 전면 투입 추정은 하지 않는다.
현재 사이트의 건조기 분류 제공 여부는 첫 실제 실행에서 확인해야 한다.

PDF는 SKU/용량/투입 방식 중 앞선 출처에서 부족한 값이 있을 때만 요청한다. 상품당 한 번의 PDF 요청에서 필요한 필드들을 함께 보완한다.
고정 페이지 제한 없이 필요한 필드만 순서대로 확인하며 모두 확보하면 중단한다. SKU만 필요하면 유효한 모델을 찾는 즉시 종료한다. 문서 끝까지 값이 없으면 재요청하지 않고 NULL과 사유를 남긴다.
PDF 모델명은 페이지 안의 명시적 모델 라벨을 순서대로 확인한다. 짧거나 유효하지 않은 후보를 거부한 뒤 같은 페이지의 다음 모델 항목을 확인하고, 유효한 첫 후보를 유지한다. 서로 다른 모델 항목은 합치지 않으며 후보·미채택 사유·선택값·페이지를 진단에 기록한다.
PDF 작업은 Windows에서도 종료 가능한 별도 프로세스에서 실행한다. 한 시도의 요청 단계는 기존 `Client.timeout`(기본 30초), 문서 열기·텍스트 처리는 `PDF_PARSE_TIMEOUT`(기본 30초)을 상한으로 사용한다. 프로세스 시작 시간도 제한에 포함된다. 종료 정리는 최대 2초까지 추가될 수 있다.
요청/문서 처리 실패는 `PDF_MAX_ATTEMPTS=3` 범위에서 최초 시도 후 최대 2회 재시도한다. 각 내부 HTTP 호출은 1회이며 대기는 재시도 전 1초·2초다. 기본 설정에서 최악의 PDF 보완 시간은 약 189초 이내(3×요청 30초+처리 30초+정리 2초, 대기 총 3초)다. 이미 열 수 있었던 PDF는 메모리에서 재사용하고, 열리지 않은 문서나 PDF가 아닌 응답만 새로 요청한다. 과도한 크기에 대한 기존 다운로드 제한은 유지한다.
시간 초과 시 실제 작업 프로세스를 종료하고 앞 페이지에서 확인한 값은 보존한다. 요청 실패·PDF 열기 실패·텍스트 추출 실패·시간 초과·명시값 미확인을 구분한다. 문서 처리 로그에는 확인 페이지, 부족한 필드, 경과시간, 확보 필드, SKU 후보 및 재시도 결과만 남긴다.
투입 방식은 Frontlader·Toplader 등 해당 제품의 명시값만 읽으며 문을 당기는 설명·사진·설치 형태로 추정하지 않는다.
투입 방식 보완으로 PDF 요청이 늘 수 있다. 실제 소요시간은 원격 재수집의 단계 시간으로 확인한다.
텍스트 없는 이미지 PDF나 지원하지 않는 라벨은 빈값/사유로 남기며 OCR은 실행하지 않는다.
기존 공백·모델 정리 후 3글자 이하인 SKU는 DRY에서만 유효하지 않은 값으로 보고 다음 출처를 확인한다. 어디에서도 유효한 모델을 얻지 못하면 SKU만 NULL로 두고 상품 행은 유지한다. 짧은 원본값과 미채택 사유는 진단에 남긴다. 4글자 이상인 값에도 기존 검증을 적용한다. 정상 모델인 `TSA523WP 8kg Active`는 임의로 축약하지 않으며 상품명 보완에서만 시리즈명과 모델 구성 부분을 구분한다. 기존 CSV 재적재는 이 새 선별 규칙으로 과거값을 다시 가공하지 않는다.
savings는 유효한 할인율의 부호를 양수로 정규화한다. 빈값은 유지하며 가격으로 할인율을 새로 계산하지 않는다. 최종가격만 있는 경우는 정상이다.
제목과 사양의 용량 충돌은 선택값과 후보를 진단 파일에 남긴다.
평점은 리뷰 첫 화면 요약만 읽고 실패는 NULL, 검증된 무평가만 0으로 저장한다.
재시도의 부분 응답을 합쳐 양수 별점과 평가 수 0건이 충돌하면 별점은 보존하고 평가 수 두 컬럼은 NULL로 남긴다.
부분 응답끼리 값을 보완해도 한 응답에서 유효한 별점·평가 수가 확인되기 전에는 `failed` 상태를 유지한다.
목록 상품정보의 개별 HTTP 400 오류는 LDY처럼 한 요청 묶음 안에서만 누적하며, 분할 요청은 같은 카운터를 공유한다.
LDY 설정 `OTTO_CROCOTILE_SINGLETON_FAILURE_LIMIT`을 사용하며 기본 3건이면 중단한다. 1~2건은 건너뛰고 다음 묶음에서는 새로 계산한다.
실행 전체 누적은 별도로 `counts.tile_http_400_failures`에 보존한다. 오류 로그에는 묶음별/전체 누적 수와 건너뜀·중단 여부가 기록된다.
최대 HTTP 3회, 시도별 30초 읽기 예산/소켓 제한, DB 연결 10초·쿼리 60초·잠금 15초 제한을 둔다.
느린 작업은 10초 간격 진행 로그를 출력한다. 남은 시간은 지금까지 측정한 처리시간 기준 추정치다.

설정값: country=SEG, account_name=OTTO. item은 상품 ID, sku는 모델명이다.
생성값: main_rank/bsr_rank, calendar_week(`w숫자`, LDY 동일), crawl_datetime(실행 호스트 시각), batch_id.
DB 생성값: id. CSV는 빈칸, INSERT 대상에서는 제외한다.
나머지는 수집/정규화값이며, 가격/할인 표시 단위는 CSV에 유지한다.
DB 숫자 컬럼에는 형식에 맞게 변환하지만 capacity는 kg 보존을 위해 문자형만 허용한다.
시작 시 컬럼·자료형·id 시퀀스/identity·NULL 허용을 확인한다. 수집 실패 가능 필드가 NOT NULL이면 중단한다.
bsr_rank도 NULL 허용이 필수다. NULL 불가이면 `table_requires_nullable:bsr_rank`로 사이트 수집 전에 중단하며 테이블은 자동 변경하지 않는다.

## 수량 확대 후 검수

1. CSV가 정확히 20열·최대 300행인지, main이 연속이고 상위 100개만 BSR이 동일하며 나머지는 NULL인지 확인한다.
2. 제외/애매한 상품과 포함된 상품을 함께 확인해 잘못 포함·제외한 URL을 모은다.
3. SKU가 해당 옵션 모델인지, 용량이 건조 용량인지, 투입 방식에 실제 근거가 있는지 확인한다.
4. 용량 충돌과 별점 failed/unrated, 개별 요청 실패를 진단 파일에서 확인한다.
5. 목표 미달이면 실제 끝/제외/중복/실패 수와 사유를 확인한다.
6. DB 삽입 수, NULL, 재적재 시 삽입 0건을 확인한다.

확대 결과 검수 후 남은 작업은 운영 테이블 전환, 전체 BAT 연결, 메일 보고, 과거 DB 보충이다.
과거 DB·수동 입력값 재사용 대상은 sku·capacity·loading_type이며, 단독 BAT는 통합 후에도 유지한다.
